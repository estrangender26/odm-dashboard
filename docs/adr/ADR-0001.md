# ADR-0001 — Temporary Hosting Strategy for the Lihok Corporate Library

**Status:** Accepted  
**Date:** 2026-08-04  
**Deciders:** Office of the President / Lihok Architecture Governance  
**Layer:** Corporate Governance

---

## Context

Lihok Technologies OPC needs a controlled corporate document library to manage policies, legal records, HR documents, finance documents, and other company-controlled content. The initial scope covers 16 top-level categories, starting with the Corporate Foundation Manual (LT-CORP-001).

Two implementation paths were available from the start:

1. Build a separate application and database for the Corporate Library immediately.
2. Host the Corporate Library temporarily inside the existing ODM Dashboard repository and database, while keeping it logically separate so it can be extracted later.

The ODM Dashboard already has proven document upload, Supabase Storage, and authentication patterns. However, the Corporate Library must not become coupled to ODM, Manila Water, facilities, equipment, milestones, governance TOC items, or SMP records.

## Decision

We will **temporarily host the Lihok Corporate Library inside the ODM Dashboard repository and database**.

This is a strategic portability decision, not a long-term architectural destination. The module will remain logically separate and will be extracted to `app.lihoktech.com` or `library.lihoktech.com` when Lihok's platform matures.

## Alternatives Considered

### Alternative A — Separate application and database from day one

- **Pros:** Cleanest separation; no risk of ODM coupling.
- **Cons:** Operational overhead for a single-tenant module with one known user base; slower initial delivery; duplicates authentication and storage setup.
- **Rejected:** The additional operational cost is not justified while Lihok has only one internal tenant and a small engineering team.

### Alternative B — Reuse ODM document tables (doc_files, smp_documents, governance_uploads)

- **Pros:** Fastest reuse of existing code.
- **Cons:** Deep coupling to ODM data models (folders, equipment, facilities, milestones, TOC items); no version history, classification workflow, or audit trail.
- **Rejected:** This would permanently entangle Lihok corporate data with customer/product data and prevent extraction.

### Alternative C — Add multi-tenancy or tenant_id from day one

- **Pros:** Future-proof for additional tenants.
- **Cons:** Premature abstraction; every query and test must carry a tenant filter before a second tenant exists.
- **Rejected:** Tenant boundaries will be introduced additively when a second tenant is onboarded.

## Consequences

### Positive

- Faster initial delivery using proven ODM Dashboard infrastructure.
- Corporate Library can reuse the existing authentication, Storage upload, and deployment pipeline without duplication.
- The schema is fully separate, making extraction straightforward.

### Negative

- The repository temporarily contains both ODM product code and Lihok corporate code.
- There is a risk that future developers will accidentally couple the Corporate Library to ODM-specific code unless boundaries are actively policed.
- Identity currently relies on the ODM Dashboard `users` table, which will need an additive migration when Lihok moves to Microsoft Entra ID.

## Extraction Plan

When the Corporate Library moves to its own application:

1. Copy the four database tables and the 16 seeded categories to the new PostgreSQL environment.
2. Create the dedicated `lihok-corporate-library` Supabase Storage bucket in the new environment.
3. Migrate active Storage objects and update `storage_bucket` / `storage_path` references if the bucket name changes.
4. Introduce `tenant_id` and update the unique constraint on `document_number` to be unique per tenant.
5. Add `external_subject_id` or migrate identity through the shared auth layer.
6. No destructive schema migration is required.

## Security Considerations

- PR 1 does not add Row-Level Security policies. Access control will first be enforced in the tRPC/API layer.
- `Confidential` and `Restricted` classifications are stored but not yet enforced by the database.
- The uploader may not approve their own document; this will be enforced in application logic.
- Approved controlled documents will be immutable; version replacement will create new version rows rather than overwrite existing Storage objects.
